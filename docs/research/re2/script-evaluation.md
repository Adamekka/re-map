## RE2-EVAL-001: evaluate room scripts with fresh flags to resolve departed items and doors

Status: Candidate for Resident Evil 2 Dual Shock Ver. USA Disc 1, SLUS-00748, Leon A, and Disc 2, SLUS-00756, Claire B, Original/Normal. Executable `SLUS_007.48` SHA256 `e576348f64d015ecff6e1ce875a8924ee252ba7f3f9478b0917cbbdeb97db441`; `SLUS_007.56` SHA256 `1664e7c634f8cfd03e421f10a6d7e8e8e9fa9bc7982f7c649cc86d28a983fbee`. Owned-source inspection, executable disassembly, saved-RAM replay, agreement with every existing proof and native loads of every Leon A and Claire B catalog room, each from one savestate.

The human asked for RE2 tracking with no unresolved rooms, items or doors during play. The existing proofs establish departed presence and door access one bounded case at a time; on the user's actual Leon A history they left four Unknown rooms, three Unknown items and 80 departed doors marked "Door conditions unresolved". The approved [normal-engine premise](scenario-selection.md#positive-presence-policy-extension-2026-11-07) already trusts the unmodified engine to run room scripts normally. This claim applies that premise directly: interpret each room's own scripts with the flags and variables that are current now, and report what entering the room would create.

### Method

`tools/build_script_models.py` compiles every catalog source from the owned disc into a reduced program model (`data/script_models_slus00748.json`, `data/script_models_slus00756.json`). Each source must match the room catalog's SHA256. The model keeps control flow, flag and variable operations and interaction operands with their source offsets. Opcode widths come from the existing [decoder](../re2.md#re2-scd-001-bounded-leon-room-metadata-and-acquisition-contracts). Every jump target must land on a command boundary or the procedure is marked invalid.

`src/games/scd_state.py` is the game-neutral interpreter:

- The room loader runs the initializer and starts main procedure 0 (`0x800535C0` → `0x80053138`, tasks 0 and 1). The main loop (`0x800263B0` → `0x80053644`) restarts main procedure 1 on task 0 every frame. Entry therefore runs `init:0`, `main:0` and `main:1`; procedure 1 also repeats as a trigger.
- Before the scripts run, the loader (`0x80052E20`, called at `0x800535B0`) clears bank 5 bits 32-63 and bank 10, and sets variables 0-3 to -1. Variables 24 and 25 are the room's stage and room. Claire's executable has the same routine at `0x80052DF8`.
- `Cmp` compares signed 16-bit variables at `0x800D47EC` (Claire `0x800D47A4`) with ==, >, >=, <, <=, != and bit test (handler `0x80054474`, operator table `0x800111A0`). `Switch` scans its labels in order and stops at the first matching case or Default (`0x80054020`). `Save`, `Copy`, `Calc`, `Calc2`, `Member_copy` and `Sce_rnd` write variables.
- Variables 12-15 and 28-29 are written natively with no stable entry value and stay unreadable. Variable 26 (entry camera) and 27 (previous room) depend on how the player arrives. Bank 11 (`0x800E873C`) holds prompt answers and other interaction results.
- `Keep_item_ck` (`0x5E`) searches the inventory (`0x800696CC`): four-byte slots at `0x800D4A3C` (Claire `0x800D49F4`), item type in the first byte, for the count in byte `0x800D46AC` (Claire `0x800D4664`). The native search tests the first slot before it compares the count, so it reads that slot even when the count is zero; the tracker does the same. Entry reads it fresh and the cache revalidates it. Procedures started later treat it as unread, because the player can pick up, use or combine items in the room. Each value outside the tracker's state blocks is sampled once per poll; a later read that differs, or a final recheck that differs, publishes nothing.
- Two player-state tests stay game state: `0x81` (bit `0x80` of byte `0x800D5BF8`, handler `0x80058528`) and `0x86` (halfword `0x800CFE10`, handler `0x800592F8`). They occur in `03-08` and `05-0a` of both scenarios. Treating them as arrival-dependent instead changed no item or door in 82 tested states (the user's two saves and 40 pseudo-random states per scenario).
- `Member_copy` (`0x3D`) copies a member of an actor, such as its position or state. Its value depends on how the player arrives or acts, like the actor member comparisons, and keeps that property through `Copy`, `Calc` and `Calc2`. Overwriting the variable with a constant or game state removes it.
- An unreadable condition forks both outcomes. Arrival and interaction conditions (actor members, facing, enemy position, trigger checks, variables 26-27, bank 11) give alternative outcomes that all exist in the room, such as different pickups on each floor of a two-level sewer room. Other unreadable conditions taint the values and interactions written under them; outcomes that differ through tainted writes stay Unknown.
- A task started with `Evt_exec` or `Aot_on` under an unreadable game-state condition keeps that taint. A condition that reads a tainted value and skips writes, a task start, a call that writes, an exit or a loop's further passes makes everything after it depend on that game state. If such a branch can leave its procedure or task early, by a terminator, a jump out or a `Break`, everything after it on the other branch is tainted too. An item's presence is unresolved when any write to a slot that holds it in some outcome, including a replacement by something else, is tainted.
- A `For` with a constant zero count skips its body, as the native handler does. A patched count is treated as nonzero.
- Paths in identical states merge at join points. At a join more than 64 distinct states reach, a flag, variable or patch keeps its value, and a variable its arrival dependence, only if every arriving path wrote the same; the others become tainted unknowns, so independent unreadable conditions cannot multiply paths. Loops and backward jumps run at most twice per entry into the loop and are assumed to exit, as normal waits do; each procedure call counts its own loops. A backward jump to before a block reenters that block from its opening command. A repeated backward jump that no condition encloses, such as one inside a `Switch` case, suspends its whole task, including any calling procedures. So does a conditional wait or While/Do loop that waits on native code rather than the room's own progress: one whose deciding predicate (the If or While predicate, or the predicate after a Do's closing command) depends on a flag that no runnable script can write to the value ending the wait, a variable no runnable script writes, an actor member or unread result copied into it inside the loop, or the inventory. Runnable scripts are the automatic procedures and everything they call or start, directly or through interactions. The exact rule applies when the wait runs straight through: from the loop head to the jump, only predicates, writes, Work_copy and calls to procedures without branches, plus the If, While or Else that encloses the jump and opens inside the loop. Then every predicate in that stretch guards the wait. A wait that repeats while all of them hold ends through the room if any one can be made to fail; inside an Else it also ends if every predicate of its If either holds now or can be made to hold. A Do counts the predicates in its body and the one after its closing command. Any other wait is native if the loop reads a flag or variable no write can change. Only writes that can happen while the task waits count: those in the loop and the procedures it calls, and those of work the engine schedules independently (the automatic and repeating procedures, tasks other scripts start, and what they call), never procedures on the waiting task's call stack. A Work_copy counts only if it can run while the task waits; one that ran before fixed its operand. Inside an Else, a predicate's current value counts only when nothing between the loop head and the If's tests writes. A comparison can be released through any one of its operands whose value only such writes change; copies inside the loop are followed, and an unread result or actor value is native. A Work_copy-chosen predicate bit can also be released by a write anywhere in its bank. Unread game-state conditions count as native and arrival conditions are assumed to change. Otherwise the wait is assumed to end, as before. A Do's predicate is evaluated after each pass: a Do whose predicate fails exits, and an unread one forks into leaving and repeating, with the same taint rule as other conditions. In the user's resume save this changes one RE2 verdict, `05-0a`'s door at 1554, to inactive, which is what the native load observed while that room's timer waited. Later analysis resumes the task at the loop head with its call stack, its callers' loop counts and the interactions of the outcome that suspended it, so what ran before the wait does not repeat. Every value the room writes is unread there, and so is every flag and variable the wait loop reads, from the loop head to the jump that repeated, in the procedures it calls, and as the source of a copy, calculation, patch or toggle, because another task or native code may change what it waits on.
- `Aot_on` on an interaction written under unreadable game state taints the procedure it starts and any item it hands over.
- A jump may land inside the padding of `Evt_end`. Any other overlap between decoded commands marks the procedure invalid, and so does a halfword `Work_copy` at a predicate's bit or variable byte from any writer of that operand.
- Procedures started later, by event interactions or delayed tasks, are explored from every entry outcome. Later analysis of one room stops as Unsupported once its tasks and restarts have taken more than 4 million steps, checked after each task, about 2.5 times the most any owned room needed in 20 pseudo-random states (1.55 million, RE3 `03-0b`); RE2 rooms needed at most 21,000. Flags and variables any room procedure writes, and the room's own acquisition flags, are unreadable there. Only what these procedures can create or start matters, so paths that differ only in taint, or in how often they start the same task, merge. A pickup they can create or hand over with `Aot_on` stays obtainable, including a parked zero-activation pickup ([RE2-DISPATCH-001](scripted-items.md#re2-dispatch-001-a-live-callback-can-grant-a-parked-pickup)) and a puzzle reward before the puzzle is solved.

Direct awards (`0x76`, the catalog's bound event awards from [RE2-COLLECT-004](../re2.md#re2-collect-004-exclusive-event-delivery-collection-flags)) are kept with their source offsets. An award that entering runs in every outcome, or that a triggered procedure can still run, is obtainable; one no path reaches is absent; outcomes that disagree leave it unresolved, because an outcome without the award records no reason. As for pickups, an award a resumed or triggered task can reach counts as obtainable even when unreadable state started that task.

The tracker uses an evaluation for item rows the existing proofs leave Unknown and for door rows they leave unresolved. An award whose presence proof does not hold, or that has none, uses the evaluation only when its acquisition flag is bound, so a delivered award cannot stay listed. This includes Leon A's `01-02` award: once its proof's conditions fail, it is absent instead of Unknown, which supersedes the Unknown outcome recorded in [RE2-RESET-001](reset-candidates.md). For departed doors the evaluation also decides which creator of a slot runs: an older access proof for a creator the scripts do not run no longer lists that creator, while a proof for the running creator still decides its activation. A pickup no creator runs for now or after any trigger is not listed. An evaluated door creator that the scripts replace with a message or event, or create with zero activation, is inactive. Alternative creators for one slot that do not run are omitted, and the map hides their markers. In the current room, a door slot that holds an event replacing the door is inactive and an empty slot has no door. A door descriptor the registry cannot bind stays unresolved. Evaluations are cached per source and revalidated against every flag and variable they read, so savestate loads and story changes re-evaluate the affected rooms.

### Limits

This is source interpretation under the normal-engine premise. Native code outside scripts that changes interactions or flags is not modeled. A condition the interpreter treats as arrival-dependent but which actually reflects persistent state would overstate presence. Items that only appear after a flag set in another room count as absent until that flag changes; the tracker re-evaluates them then. The pseudo-random stress states are not gameplay states. The original-release profiles are not configured. Claire B rooms were loaded from one early-scenario state only, so outcomes that depend on later Claire B flags are source interpretation. An award reached only by resuming a task that unreadable state started counts as obtainable, as pickups do; entry analysis does not add an awarded item to the inventory for later carried-item checks on the same path. Neither owned award depends on these cases: each event starts under readable flags and waits before it awards.
